# Collections 2026 qualified results — 2026-08-13

The retained run used the deterministic `scripts/run-collections2026.ps1`
gate: five pre-run CPU samples averaged 9.2% against a 10% limit, every process
was pinned to logical CPU 0, and implementations were interleaved for ten
independent runs. Compilation and managed warmup were excluded from timing.
Every process produced checksum `50000000000000` and final length `5000000`.

Sollang and C++ reported capacity `16777216`; Rust reported `14080261` in the
retained first run; Go and .NET do not expose capacity through their public
collection APIs. Sollang uses one combined key/control allocation of
83,886,096 bytes for this capacity: 16,777,216 four-byte keys, 16,777,216
control bytes, and a 16-byte mirrored control tail. Its allocator counters are
not yet exposed, so the table reports them as unavailable rather than inferring
them from layout. Peak working set was sampled every 5 ms during execution.

Toolchain and host:

- Intel Core Ultra 9 275HX, 24 cores / 24 logical processors
- Windows 11 Pro 10.0.26200
- Sollang compiler built from this working tree, LLVM `-O3`
- clang 22.1.8, rustc 1.97.0, Go 1.26.5
- .NET SDK 11.0.100-preview.7, NativeAOT publish
- OpenJDK 17.0.19

This evidence supports strong memory efficiency and competitive native
performance among the measured implementations: Sollang has the lowest sampled
peak working set and is faster than the measured Java, Rust, C++, and Go
baselines. .NET NativeAOT is still 3.37x faster on median latency.
Allocator-exact Sollang metrics remain unavailable, so no overall “fastest” or
universal best-performance claim is accepted. The raw summary is retained at
`artifacts/benchmarks/collections2026/results-20260813-041034.json`.
